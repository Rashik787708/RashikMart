# RashikMart Database Configuration

Two database backends are supported and selected at startup through the
`DB_TYPE` environment variable:

| Environment          | DB_TYPE        | Database                      |
|----------------------|----------------|-------------------------------|
| Local development    | `h2` (default) | H2 file database (`./data`)   |
| Render (production)  | `postgres`     | Render-managed PostgreSQL     |

```
             RashikMart
                 |
        +--------+--------+
        |                 |
     LOCAL              RENDER
        |                 |
    DB_TYPE=h2      DB_TYPE=postgres
        |                 |
       H2          Render PostgreSQL
        |                 |
   Local data       Persistent data
```

No PostgreSQL is required to build or run the project locally, and no H2 is
used on Render.

---

## 1. How the backend is selected

`com.rashik.rashikmart.config.DatabaseConfig` resolves the backend in this
order:

1. System property `db.type` — set by the Maven test suite to `h2` so unit
   tests always run against an in-memory H2 database.
2. Environment variable `DB_TYPE`.
3. Default: `h2` (local development keeps working out of the box).

### H2 (local)

The existing file-based H2 database under `./data` is used unchanged, so all
current local users/products/data remain available:

- JDBC URL (default): `jdbc:h2:./data/rashikmart`
- User (default): `sa`
- Password (default): `WE`

All three are overridable with `DB_URL`, `DB_USER`, `DB_PASSWORD` env vars or
the `db.url` / `db.user` / `db.password` system properties. The local
`.mv.db` files are never deleted or recreated.

### PostgreSQL (Render)

When `DB_TYPE=postgres`, the app connects through Render's `DATABASE_URL`
internal connection string. Never hardcode or commit this value.

The URL may be supplied as either:

```text
postgresql://user:password@host:5432/database?sslmode=require
```

or already prefixed:

```text
jdbc:postgresql://user:password@host:5432/database?sslmode=require
```

`DatabaseConfig` parses the embedded credentials out of the URL (never
logged), keeps the SSL/query options on the JDBC URL, and hands them to
HikariCP as `username`/`password` settings. If the URL contains no
credentials, `DB_USER` / `DB_PASSWORD` are used.

## 2. Schema initialization

`com.rashik.rashikmart.config.DatabaseContextListener` runs on application
startup and:

1. Creates every table with `CREATE TABLE IF NOT EXISTS` (safe on both H2 and
   PostgreSQL for existing databases).
2. Applies `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` for legacy columns.
3. Seeds the default admin (`admin@rashikmart.com`) only if the email is
   absent.
4. Seeds the demo seller + 48-product catalog + demo buyer **only when the
   products table is empty** (a fresh database), via
   `src/main/resources/seed_catalog.sql`.

No `DROP TABLE` on application tables, no `DROP ALL OBJECTS`, no `TRUNCATE`,
and no `DROP DATABASE` is ever executed during normal startup.

The schema uses portable, standard SQL so one definition works on both
databases:

- identifiers: `INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (H2 and
  PostgreSQL both support this)
- `BOOLEAN`, `DECIMAL(12,2)`, `TIMESTAMP DEFAULT CURRENT_TIMESTAMP`,
  `VARCHAR`
- foreign keys with `ON DELETE CASCADE`, unique constraints

All DAO queries (`UserDAO`, `ProductDAO`, `OrderDAO`, `CartDAO`,
`ReviewDAO`) are plain ANSI SQL and run unchanged on H2 and PostgreSQL.

### Seeding on PostgreSQL

H2's `org.h2.tools.RunScript` is H2-specific. On PostgreSQL the seed script
is executed statement-by-statement through JDBC with the portable
`com.rashik.rashikmart.util.SqlScriptRunner`. The seed SQL itself is plain
standard SQL (idempotent: the seller and each product are inserted only when
they do not already exist).

## 3. Environment configuration

### Local (Windows) — no setup required

```text
DB_TYPE=h2
```

Optional overrides:

```text
DB_URL=jdbc:h2:./data/rashikmart
DB_USER=sa
DB_PASSWORD=WE
```

### Render Web Service (free tier) — H2 in-memory

The `Dockerfile` ships with these defaults, so a fresh Render Web Service runs
on H2 with **no database environment variables required**:

```text
DB_TYPE=h2
DB_URL=jdbc:h2:mem:rashikmart;DB_CLOSE_DELAY=-1
DB_USER=sa
DB_PASSWORD=WE
```

The schema and the seeded catalog are created automatically on every boot
(`DatabaseContextListener`). Because Render's free filesystem is ephemeral and
in-memory H2 lives only as long as the JVM:

- Data written at runtime (new users, orders, reviews) is **lost** on every
  deploy, restart, or after the free instance spins down from inactivity.
- Product images uploaded by sellers are likewise ephemeral.
- The seeded seller and 48-product catalog always reappear on boot.

This is fine for a demo/portfolio deployment. For durable live data, either set
`DB_TYPE=postgres` with a `DATABASE_URL`, or attach a Render Disk and point a
**file** H2 database at it:

```text
DB_TYPE=h2
DB_URL=jdbc:h2:/var/data/rashikmart
RASHIKMART_UPLOAD_DIR=/var/data/product-images
```

> Note: Render dashboard environment variables override the `Dockerfile`
> defaults. If the service still has `DB_TYPE=postgres`, either delete that
> variable or set `DB_TYPE=h2` explicitly.

### Free durable database — Neon / Supabase (recommended for Render)

Render's own PostgreSQL free tier expires, but you can point `DATABASE_URL` at a
**free, externally-hosted PostgreSQL** instead. The app is provider-agnostic —
it only needs a standard `postgresql://` connection string.

**Neon (https://neon.tech)**

1. Sign up, create a project (choose the region closest to your Render service).
2. Copy the **connection string** from the dashboard, e.g.:
   ```text
   postgresql://neondb_owner:YOUR_PASSWORD@ep-cool-name-123456.us-east-2.aws.neon.tech/neondb?sslmode=require
   ```
3. On Render → Web Service → **Environment**, set:
   ```text
   DB_TYPE=postgres
   DATABASE_URL=postgresql://neondb_owner:YOUR_PASSWORD@ep-...neon.tech/neondb?sslmode=require
   ```
4. Redeploy. Tables are created and the catalog is seeded automatically on first
   boot; all later registrations, orders and reviews persist across restarts.

**Supabase (https://supabase.com)** — same steps; use the **Connection pooling**
URI (port `6543`). If the password contains special characters, percent-encode
them (e.g. `@` → `%40`).

Notes:

- The app parses the username/password out of the URL (percent-decoded) and
  preserves `sslmode=require`, so the exact string shown by the provider works.
- Free-tier databases may suspend when idle; the first request after a pause is
  slower while the database wakes.
- If you previously set `DB_TYPE=h2`, change it to `postgres` — dashboard values
  override the `Dockerfile` defaults.
- `/api/v1/health` returns the live database status if you need to confirm the
  connection after deploying.

### Render-managed PostgreSQL (legacy)

```text
DB_TYPE=postgres
```

Create a Render PostgreSQL database and paste its **Internal Database URL**
into the Web Service environment variable `DATABASE_URL`.

## 4. Authentication (unchanged)

- Registration inserts the user (BCrypt-hashed password) into the selected
  database.
- Login looks the user up in the database and verifies the BCrypt hash.
- Passwords are never stored in plaintext, never sent to
  localStorage/cookies, and never placed in the `HttpSession`.
- The session may expire while the account stays in the database, and
  logout never deletes the account.

## 5. Build and test

Unit tests run against in-memory H2 (forced via the Maven Surefire system
properties `db.type=h2` and `db.url=jdbc:h2:mem:rashikmart_test;DB_CLOSE_DELAY=-1`).

```bash
mvn clean test
mvn clean package -DskipTests
```
